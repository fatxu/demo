## Approach Comparison

### Approach A: Stream per-file (current)
```
for each file:
    openssl enc | aws s3 cp -   ← one TLS handshake per file
```

### Approach B: Batch encrypt → folder → `aws s3 cp --recursive`
```
Phase 1: openssl enc → /tmp/batch/   (N files encrypted to disk)
Phase 2: aws s3 cp /tmp/batch/ s3://... --recursive
```

---

## Deep Analysis

### The `--recursive` internals

`aws s3 cp --recursive` is **not** magic. Under the hood it:
1. Lists local files
2. For each file, spawns an internal thread and calls `PutObject` — still **one TLS connection per file** (connection pooling helps marginally, reuses ~keep-alive connections within the same process)
3. The key difference: **connection reuse across files** within one CLI process vs. 5M separate process spawns

So the real question is: **how much does per-process spawn cost vs. connection reuse gain?**

---

## Cost Breakdown Per File

| Cost Item | Stream (A) | Batch+Recursive (B) |
|---|---|---|
| `openssl` process spawn | 1× per file | 1× per file |
| `aws s3 cp` process spawn | 1× per file | **~0** (one process, internal threads) |
| TLS handshake | 1× per file | **~shared** (keep-alive pool) |
| Disk write (encrypted) | **0** | 1× per file |
| Disk read (for upload) | 1× (source) | 2× (source + encrypted copy) |
| `/tmp` space needed | ~0 | = batch_size × avg_file_size |

### Process spawn cost on AIX
KSH `fork+exec` for `aws` (a Python process) on AIX is heavy: **~50–150ms per spawn**, including Python interpreter startup. Over 5M files:

```
5,000,000 × 100ms = 500,000 seconds ≈ 138 hours  (single-threaded, spawn cost alone)
```

With 12 workers: **~11.5 hours just in spawn overhead** — this is the dominant cost in Approach A.

`--recursive` eliminates 5M Python spawns → replaces with internal thread scheduling (~microseconds each).

---

## Approach B: The Real Numbers

### `/tmp` space constraint
You can't encrypt all 5TB to disk. So batch size must be bounded:

```
batch = 10,000 files × 1MB avg = 10 GB per worker batch
12 workers × 10 GB = 120 GB /tmp needed
```
Manageable if AIX has scratch space. But this adds a **drain-and-refill cycle**:

```
while files remain:
    encrypt 10,000 files → /tmp/batch/    (~encrypt throughput limited)
    aws s3 cp /tmp/batch/ --recursive     (~upload throughput limited)
    rm /tmp/batch/*
```

These two phases are **sequential within each batch** — you lose pipeline parallelism unless you interleave batches.

### Optimal B: Double-buffer with 2 batch dirs

```
Worker owns: /tmp/batch_A/  /tmp/batch_B/

Round 1:  encrypt → batch_A  |  (upload batch_B from prev round)
Round 2:  encrypt → batch_B  |  upload batch_A
```

This fully overlaps encrypt CPU with upload I/O — but requires careful coordination in KSH (background jobs + semaphore files).

---

## Honest Performance Projection

### Approach A (stream, 12 workers)
```
Per file: 50ms openssl spawn + 100ms aws spawn + 80ms TLS + transfer
≈ 250ms/file per worker
12 workers: ~48 files/sec
5M files: ~29 hours
```

### Approach B (batch encrypt + recursive, 12 workers, double-buffer)
```
Encrypt phase: openssl is fast, ~200 MB/s per core
  5TB ÷ (200MB/s × 12) ≈ 35 minutes pure encrypt time (CPU-bound)

Upload phase: 100MB/s network ÷ 12 workers = 8.3 MB/s per worker
  But --recursive reuses connections, removes 5M × 100ms TLS overhead
  = 500,000 seconds saved = 138 hours saved vs A
  5TB ÷ 100MB/s = ~14 hours pure transfer time (network-bound)

Total ≈ 14–16 hours  (network ceiling dominates)
```

---

## Verdict

**Approach B wins decisively**, for one reason: **eliminating 5M Python/AWS CLI process spawns**.

`--recursive` turns 5M heavyweight process forks into internal thread dispatches. That's the single biggest optimization available within KSH-only constraints.

The disk write cost (encrypt to `/tmp`) is real but minor — sequential writes at 200+ MB/s are fast, and the double-buffer pattern hides them behind concurrent uploads.

## Recommended Implementation: B with double-buffer

```ksh
#!/usr/bin/ksh
# =============================================================================
# upload_encrypt_batch.ksh
# Strategy: batch encrypt to tmp → aws s3 cp --recursive (double-buffer)
# AIX 7.2, KSH, 12 vCPU, 100MB/s network
# =============================================================================

SOURCE_DIR="/data/files"
S3_BUCKET="s3://your-bucket"
S3_PREFIX="encrypted"
WORKERS=12
BATCH_SIZE=5000            # files per batch per worker; tune to /tmp space
PASSPHRASE="your-passkey"
TMP_BASE="/tmp/uploader"
CHECKPOINT="/var/log/upload_done.log"
FAILED_LOG="/var/log/upload_failed.log"
WORK_DIR="/tmp/upload_work"

mkdir -p "$WORK_DIR" "$TMP_BASE"
touch "$CHECKPOINT" "$FAILED_LOG"

# ── Build remaining file list ─────────────────────────────────────────────────
ls "$SOURCE_DIR" | grep '\.pdf$' | sort > "$WORK_DIR/all.txt"
sort "$CHECKPOINT" > "$WORK_DIR/done.txt"
comm -23 "$WORK_DIR/all.txt" "$WORK_DIR/done.txt" > "$WORK_DIR/remaining.txt"

TOTAL=$(wc -l < "$WORK_DIR/remaining.txt")
echo "[$(date)] Remaining: $TOTAL files"

# Split into per-worker shards
split -l $(( (TOTAL + WORKERS - 1) / WORKERS )) \
    "$WORK_DIR/remaining.txt" "$WORK_DIR/shard_"

# ── Worker: double-buffer encrypt + upload ────────────────────────────────────
run_worker() {
    typeset wid=$1
    typeset shard=$2
    typeset log="$TMP_BASE/worker_${wid}.log"
    typeset dir_a="$TMP_BASE/w${wid}_a"
    typeset dir_b="$TMP_BASE/w${wid}_b"
    typeset active=$dir_a fill=$dir_b
    typeset batch_files="" count=0 ok=0 fail=0
    typeset upload_pid=""

    mkdir -p "$dir_a" "$dir_b"
    echo "[$(date)] Worker $wid started" >> "$log"

    flush_and_swap() {
        # Wait for previous upload to finish
        [[ -n "$upload_pid" ]] && wait "$upload_pid"

        # Upload current active dir in background
        typeset udir=$active
        (
            aws s3 cp "$udir/" "${S3_BUCKET}/${S3_PREFIX}/w${wid}/" \
                --recursive --no-progress 2>>"$log"
            if [[ $? -eq 0 ]]; then
                # checkpoint all files in this batch
                for f in "$udir"/*.enc; do
                    base="${f##*/}"
                    echo "${base%.enc}" >> "$CHECKPOINT"
                done
                (( ok += $(ls "$udir" | wc -l) ))
            else
                for f in "$udir"/*.enc; do
                    base="${f##*/}"
                    echo "${base%.enc}" >> "$FAILED_LOG"
                done
                (( fail += $(ls "$udir" | wc -l) ))
            fi
            rm -f "$udir"/*.enc
        ) &
        upload_pid=$!

        # Swap buffers
        if [[ "$active" == "$dir_a" ]]; then
            active=$dir_b; fill=$dir_a
        else
            active=$dir_a; fill=$dir_b
        fi
        count=0
    }

    while IFS= read -r filename; do
        [[ -z "$filename" ]] && continue
        src="$SOURCE_DIR/$filename"
        [[ ! -f "$src" ]] && continue

        # Encrypt into fill buffer
        openssl enc -aes-256-cbc -pbkdf2 -iter 100000 \
            -pass "pass:${PASSPHRASE}" \
            -in "$src" -out "$fill/${filename}.enc" 2>>"$log"

        if [[ $? -ne 0 ]]; then
            echo "$filename" >> "$FAILED_LOG"
            continue
        fi

        (( count++ ))

        # Batch full → flush
        if [[ $count -ge $BATCH_SIZE ]]; then
            # swap active→upload, fill becomes new active for encrypting
            typeset tmp_swap=$active
            active=$fill
            fill=$tmp_swap

            [[ -n "$upload_pid" ]] && wait "$upload_pid"
            (
                aws s3 cp "$active/" "${S3_BUCKET}/${S3_PREFIX}/w${wid}/" \
                    --recursive --no-progress 2>>"$log"
                if [[ $? -eq 0 ]]; then
                    for f in "$active"/*.enc; do
                        base="${f##*/}"; echo "${base%.enc}" >> "$CHECKPOINT"
                    done
                else
                    for f in "$active"/*.enc; do
                        base="${f##*/}"; echo "${base%.enc}" >> "$FAILED_LOG"
                    done
                fi
                rm -f "$active"/*.enc
            ) &
            upload_pid=$!

            active=$fill
            count=0
        fi

    done < "$shard"

    # Final partial batch
    if [[ $count -gt 0 ]]; then
        [[ -n "$upload_pid" ]] && wait "$upload_pid"
        aws s3 cp "$active/" "${S3_BUCKET}/${S3_PREFIX}/w${wid}/" \
            --recursive --no-progress 2>>"$log"
        for f in "$active"/*.enc; do
            base="${f##*/}"; echo "${base%.enc}" >> "$CHECKPOINT"
        done
        rm -f "$active"/*.enc
    else
        [[ -n "$upload_pid" ]] && wait "$upload_pid"
    fi

    rmdir "$dir_a" "$dir_b" 2>/dev/null
    echo "[$(date)] Worker $wid done" >> "$log"
}

# ── Launch workers ────────────────────────────────────────────────────────────
pids=""
i=0
for shard in "$WORK_DIR"/shard_*; do
    run_worker $i "$shard" &
    pids="$pids $!"
    (( i++ ))
done

for pid in $pids; do wait $pid; done

echo "[$(date)] Done. Uploaded: $(wc -l < "$CHECKPOINT")  Failed: $(wc -l < "$FAILED_LOG")"
```

## `/tmp` Space Required

```
12 workers × 2 buffers × 5,000 files × 1MB = 120 GB
```

If `/tmp` is tight, reduce `BATCH_SIZE` to 1000 → 24 GB. The tradeoff is more `--recursive` invocations (more TLS handshake amortization loss), but still far better than Approach A.
